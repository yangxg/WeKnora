# ResearchFlow Customizations

This ledger records every ResearchFlow-specific divergence from Tencent/WeKnora upstream on the `researchflow-ext` branch.

## Branch discipline

- `main` only mirrors `upstream/main`; no ResearchFlow-specific commit belongs on `main`.
- Synchronize `main` with `git fetch upstream` followed by `git merge --ff-only upstream/main`.
- Before each W-track substage, synchronize `main`, then merge the synchronized `main` into `researchflow-ext`.
- Keep extensions on connector, parser, provider, or DTO plugin surfaces whenever possible.
- Before changing a core pipeline, add the proposed divergence to this ledger and record in a ResearchFlow ADR why the plugin surface is insufficient.
- Evaluate every customization for contribution to upstream and record expected resynchronization impact.

## Entry requirements

Each entry must record its W-track stage, scope, reason, changed files, tests, upstream contribution suitability, and expected impact when resynchronizing with upstream.

## W2b1 notes

- **No live call was made to any of the four registries.** Every request shape, envelope, field name and limit assertion comes from official documentation replayed against an `httptest` server. Real calls need explicit user authorization plus a governed project ADR (ADR-0012 §10), so live behaviour remains unverified by construction.
- **ADR-0012 §9 item 2 is now resolved.** Verified against `developers.openalex.org` on 2026-08-03: the current OpenAlex model is key-only, the key is sent as the `api_key=` query parameter with no header form, and there is **no polite pool and no `mailto` convention**. Content download is metered separately from list and search, which is one more reason this lane never downloads anything. Also confirmed: `doi` is returned as a resolver URL (so `NormalizeDOI`'s prefix stripping is the common path, not an edge case), `abstract_inverted_index` is documented as "the abstract as an inverted index (word positions)", and `per_page` — with an underscore — caps at 100.
- **ADR-0012 §9 item 5 is confirmed and remains a deployment precondition.** NBK25497 is explicit that supplying `tool` and `email` in requests is not registration: "these values must be registered with NCBI", and an unregistered IP that breaches policy is restored only after registration and email validation. No code can establish this.
- **Two verification gaps are left fail-closed rather than guessed.** OpenAlex's `type` has no enum in its OpenAPI spec (six documented "common values"), and PubMed's `[pt]` vocabulary page was network-blocked during implementation. Both clients therefore map only the terms they can cite and refuse the rest, so widening either map is a documentation task with a citation, not an edit. The cost is a filter a manifest could have had; the alternative cost is a filter that matches nothing and reads as an empty topic.
- **A cross-provider identity question is open for W2b2, and it is a contract question, not a bug.** arXiv's Atom API exposes no DataCite DOI, so an arXiv-only candidate's strongest identity is `arxiv:2401.00001` — and `arxiv:` is **not** a form `canonicalize_reference` accepts (ADR-0012 §3 adds only `doi:`). The same preprint reached through OpenAlex arrives as `doi:10.48550/arxiv.2401.00001`, a form that does canonicalize. So the connector needs a decided answer for what canonical reference an arXiv-only candidate carries into the inbox, and deriving the DataCite DOI from the e-print id would be asserting an identifier we never observed. Per ADR-0012's own sequencing — audit before contract, contract before code — this belongs in W2b2's contract step.
- **Retry classification is uniform and deliberately narrow across all four:** 429 and 5xx only, `Retry-After` honoured when sent, three attempts. `403` is terminal everywhere — on Crossref it is a human's block, on OpenAlex an exhausted budget, on NCBI a blocked address — and in each case retrying is the behaviour that caused it.

## W2a2 notes

- **`InboxItem.origin` is sufficient; no new ADR is needed.** The W2a0 audit left open whether ResearchFlow's single-string inbox provenance could express *which saved query* produced a candidate. It can: every candidate carries `SourceResourceID = query_id` plus `saved_query_id`, `discovery_source_id`, `discovery_project_id` and `discovery_provider` in `Metadata`, so an origin string can be composed from the row without inventing a field. Composing it is a ResearchFlow-side step, and the real `read_inbox` is still unimplemented there by design (live integration is unauthorized), so W2a3 owns the mapping.
- **The query text never leaves configuration.** It is absent from log lines, from `PartialFetchError` details (which reach the sync log), from parse errors, from `ListResources` output (that response feeds a settings UI over HTTP and this connector does not control whether it is logged), and from candidate metadata. Only `query_id` travels.
- **`Validate` deliberately makes no vendor call**, diverging from the RSS connector, which fetches every feed. Running the saved queries to validate a row would spend quota — 500 calls a month on the free tier — every time someone opens the settings drawer.
- **A candidate is identified by query *and* URL.** Two saved queries finding the same page produce two candidates with distinct provenance rather than one whose origin depends on which query ran last. The duplicate is refused downstream by promotion's canonical-URL and content-hash dedup, which is the gate that exists for it.
- **An oversized landing page is refused, not truncated.** Truncating would still ingest a body, and its content hash would then describe something that is not the page.
- **Three failure granularities, verified by mutation.** A candidate that fails is left out of the new cursor so it retries; a query whose search fails carries its prior progress forward untouched and reports partial; every query failing returns no cursor at all. Mutating each of the three — and the two leak assertions — makes the corresponding test fail.

## W2a1 notes

- **No live call was made.** Every request-shape, field-name and error-code assertion comes from the official Doubao documentation and its curl/Python samples, replayed against an `httptest` server. Calling the real endpoint needs explicit user authorization plus a governed project ADR, so anything about live behaviour remains unverified by construction — including whether `Summary` is actually populated at the documented 500–1000 characters.
- **What W2a2 inherits from the client.** `DiscoveryProfile.Options()` is the only way discovery reaches the wire, and it writes `SearchType`/`NeedContent`/`NeedURL` as constants. `Options.Validate()` is exported so the connector can reject a bad manifest before materialization rather than on the first scheduled search. `Response.Dropped` counts hits refused for lacking an absolute `http(s)` URL — the connector should surface it rather than treat a short page as a complete one.
- **Retry classification is deliberately narrow.** Only `10500` and `700429`, HTTP 429 and HTTP 5xx are retried; an unrecognized business code is terminal, because the free tier is 500 calls a month and retrying an unclassified failure spends quota to learn nothing. `Retry-After` is honoured when sent.
- **Go toolchain in this environment.** `go build ./...` needs `-buildvcs=false` (the container cannot read the repository's VCS state), and any package reaching `sqlite-vec-go-bindings/cgo` needs `libsqlite3-dev` installed in the image first.
- **Two upstream test failures here are environmental, not regressions.** `internal/handler`'s `TestPutTenantParserConfigAdminPreservesRedactedSecrets` PUTs `https://example.com/mineru`, which `validateParserEngineOutboundURLs` rejects because this network resolves the host into `198.18.0.0/15` — the same DNS artifact already noted for the datasource connectors. `internal/application/service`'s `TestTenantAPIKeyServiceAuthenticateThrottlesLastUsedUpdates` fails only under the full-package race run and passes on three consecutive isolated runs.

## W2a0 findings carried into ResearchFlow ADR-0011

Read-only audit on this baseline; no fork production change proposed or made:

- **`DataSourceConfig.Settings` already carries arbitrary discovery options to a connector at zero core cost.** Every `Connector` method receives `*types.DataSourceConfig`, so a typed options struct decoded from `Settings` needs no interface change. `Settings` is untyped, unvalidated and stored in clear, so validation is the connector's obligation — ResearchFlow validates ahead of materialization rather than trusting the row.
- **The cursor is persisted even when a fetch fails hard.** `datasource_service.go` deliberately writes back a non-nil cursor on `fetchErr` so transient outages do not force a full re-ingest. ADR-0009 §9's "cursor does not advance when the whole page fails" is therefore a *connector* obligation — return a nil cursor — not a core guarantee.
- **`web_search_providers` has no UNIQUE constraint on `(tenant_id, name)`** (`migrations/versioned/000030_web_search_providers.up.sql`). Referencing a provider instance by name is ambiguous by construction; a name-based reference must be fail-closed on a uniqueness check, or use the id.
- **Nine web-search providers are registered, not eight.** `registerWebSearchProviders` includes zhipu alongside bing/google/baidu/duckduckgo/searxng/tavily/ollama/keenable. ADR-0009 recorded eight at this same baseline; corrected in ADR-0011.
- **`initConnectorRegistry()` takes no arguments**, and connector constructors such as `rss.NewConnector()` take none either. A discovery connector that needs a vendor client must construct it from its own config rather than receive it — which is what makes the shared-client route a zero-blast-radius change.
- **`UpdateDataSource` force-preserves stored credentials** regardless of the request body, while letting `Type`/`ResourceIDs`/`Settings` through. Re-materializing a manifest therefore cannot clobber the key; idempotent materialization depends on this.
- **`POST /data-sources` accepts a client-supplied `id`** (`handler/datasource.go` binds the request into `types.DataSource` and forces only `TenantID`), which is what makes a deterministic id addressable in the first place.
- **Raw query logging already exists on the provider surface.** `web_search/keenable.go:80` logs `query=%q`. ADR-0009 §9 forbids copying it; W2a1 acceptance must capture logs as a counter-example.

## W1 findings carried into ResearchFlow ADR-0010

Measured on this baseline, test-only, no fork production change proposed:

- **Parent-child splitting loses the range on documents with tables.** `SplitParentChild` re-splits each parent's own `Content` and shifts child offsets by `parent.Start`; that arithmetic is sound only while `parent.Content == text[parent.Start:parent.End]`, which the prepended table header violates. At parent=160/child=60: `single_table` 5 of 10 children unreadable at their range (1 prefixed parent), `two_tables` 5 of 14 (1 prefixed parent), `headings_and_table` 7 of 10 (2 prefixed parents); prose and protected-span corpora 0 broken. Parents themselves always satisfy the contract. Governed knowledge bases must therefore pin `chunking_config.enable_parent_child = false`. Fail-closed on the ResearchFlow side (`locator_mismatch`), so it costs recall on tables, never correctness.
- **Image resolution rewrites markdown before chunking.** `knowledge_process.go` runs `ResolveAndStore` / `ResolveRemoteImages` ahead of splitting, so offsets address the rewritten body when a locally promoted `.md` carries resolvable images. Fail-closed; revisited at W3.
- **Query text reaches logs and langfuse spans on the search path.** Not on the certified `hybrid-search` route's chat pipeline, but real integration must still disable query logging and telemetry before any governed knowledge base is pointed at a live deployment.
